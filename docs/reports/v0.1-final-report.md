## C. 开源调研结论

（GitHub 访问受本机网络策略限制，未能 clone；基于公开资料与已知架构的对照分析）

| 项目 | Windows | JSONL 监听 | 中断检测 | Empty Response | Silent Stop | 自动 Resume | 借鉴 |
|---|---|---|---|---|---|---|---|
| cheapestinference/claude-auto-retry | ✗(tmux) | ✗ | pane 尾部 pattern | ✗ | 部分 | send-keys | 检测/重试状态机与终端后端分离的思路 |
| reglisseblip/claude-auto-retry-windows | psmux | ✗ | pane tail | ✗ | 部分 | psmux send-keys | Windows 会话管理，但依赖 psmux |
| zhangfeiyang/claude-auto-retry | SendKeys | ✓(daemon) | 错误 pattern | ✗ | ✗ | WScript SendKeys | SessionStart 启动 daemon、JSONL 轮询；SendKeys 风险高被拒绝 |
| Anthropic Hooks | ✓ | — | Stop/StopFailure | — | — | block 无效 | StopFailure 仅记录不能 block |

**结论**：现有项目全是 terminal-first（pane 尾部 pattern + 按键注入），无一实现 empty-response / silent-stop / 协议验证 / 打分。本项目的 JSONL-first + interruption score + side-effect guard 是新增核心能力。参考其「检测与注入分离」：V0.1 检测全走 JSONL，resume 只打印 prompt 不注入。

## D. 工具架构

```text
JSONL --IncrementalReader(byte offset+partial line)--> Normalizer --> StateMachine
   StateMachine --snapshot--> Detectors(empty/repeated/silent/api) --> Scorer(0-100)
   Scorer -->=threshold--> SafetyGuard(side-effect/waiting-user) --> EventLog(jsonl+text)
   dry-run(默认): 只记录；--auto-resume: experimental 仅打印 prompt
```

分类：NORMAL / NORMAL_END / TOOL_RUNNING / WAITING_USER / API_INTERRUPTED / EMPTY_RESPONSE / REPEATED_EMPTY_RESPONSE / SUSPECTED_SILENT_INTERRUPTION / SIDE_EFFECT_UNKNOWN / ROUTE_SWITCH_SUSPECTED / UNKNOWN。

## I. 已知限制

- JSONL 不含原始 SSE 帧，无法直接证明 `message_stop` 缺失；只能从 `stop_reason` 缺失/usage=0 反推
- ccSwitch `proxy_request_logs.first_token_ms` 大多为 NULL，流级断流证据有限
- `--auto-resume` 仅打印 prompt，不注入终端（V0.1 有意为之）
- 阈值由 2 个真实样本 + 合成 fixture 校准，样本量小

## J. ccSwitch / Routing / 模型切换专项结论

- `ccSwitch involvement`: **LIKELY**（间接）
- `routing involvement`: POSSIBLE（routing 开启，监听 127.0.0.1:15721；settings.json `ANTHROPIC_BASE_URL` 指向本地路由）
- `provider hot-switch involvement`: **LIKELY** —— session 内模型切换达 27 次；每次异常 turn 前都存在 `<synthetic>` 错误消息（API Error 注入 transcript）与模型跳变
- `model-switch involvement`: LIKELY（A 前 `glm-5.3→k3`；B 在 `kimi-k3` 多次跳变链中）
- `protocol-conversion involvement`: **CONFIRMED**（`chatcmpl-*` 消息 ID + usage 全 0 + stop_reason 缺失，证明响应经 OpenAI↔Anthropic 转换层且不完整）
- `upstream provider involvement`: **CONFIRMED**（B 期间 6 连发 503 `no available channels`；429/503/502 共 800+ 次）
- 时间相关性：503 错误簇与样本 B 空消息窗口（13:12:23-13:12:44）完全重叠
- 最可能故障层：**公益站上游容量/可用性 + 协议转换层对不完整上游响应的"正常化"包装**。ccSwitch 路由本身未发现直接 bug，但热切换放大了上下文不一致风险（13:14:30 那次请求 input_tokens 仅 154）。
